# Music Royalty Statement Pipeline

An end-to-end pipeline that turns messy music royalty statements from three
distributors, each with a different file format, into one validated SQL
warehouse. It then uses that warehouse to answer the question an
investment team asks before pricing a music catalog: *"how much does this
catalog earn, how fast is that falling, and how concentrated is the risk?"*

## Why this project

I built this after comparing my resume against a Royalty Data Specialist
posting at a music-catalog investment company. The core of that role is
reviewing, validating, and processing royalty statements from distributors
and DSPs. It also asks the analyst to investigate inconsistencies and
missing information, turn complex financial reports into standardized
datasets, automate repetitive work in Python, and feed pricing and
underwriting decisions. My other projects cover ETL, data quality, and
SQL warehousing, but none of them are in music or royalties. This project
closes that gap.

## Data source

**Streams are real.** The source is Spotify's weekly Top 200 chart for 63
countries, January 4 – October 18, 2019 (42 weeks, **527,170 rows**,
17,225 tracks). It was scraped from spotifycharts.com and published under
an MIT license at
[github.com/kiewic/spotify-charts](https://github.com/kiewic/spotify-charts).
Download it into `data/raw/` first (it is ~62 MB and git-ignored):

```
curl -L -o data/raw/spotify-charts.csv https://raw.githubusercontent.com/kiewic/spotify-charts/master/spotify-charts.csv
```

**Statements are synthetic.** Real royalty statements are private, so
`generate_statements.py` turns the real stream counts into monthly
statements from three fictional distributors. Their layouts, per-stream
rates, FX rates, and fees are illustrative assumptions:

| | Distributor A | Distributor B | Distributor C |
|---|---|---|---|
| File | CSV | Excel with a 2-row preamble + TOTAL footer | Semicolon-delimited CSV |
| Currency | USD | EUR | GBP, net of a 9% distribution fee |
| Track key | Spotify track ID | **none**: title + artist only | `spotify:track:<id>` URI |
| Territory | ISO-2 code | full country name | ISO-3 code |
| Dates | `YYYY-MM-DD` | `MM/DD/YYYY` | `DD.MM.YYYY` |

Per-stream rates use four illustrative market tiers (USD 0.0045 / 0.0035
/ 0.0012 / 0.0006). These are not real contract rates.

Known data-quality issues were then **deliberately injected**, and each
one was logged to `data/reference/injection_manifest.csv`. The ETL never
reads that file. It has to find every issue on its own, and
`evaluate_checks.py` scores it afterwards.

## Architecture

```
data/raw/spotify-charts.csv          real weekly chart streams (download, see above)
data/reference/                      master catalog, territories, FX, injection manifest
data/statements/distributor_{a,b,c}/ 30 generated statement files (regenerated by step 1)
scripts/generate_statements.py       1. real streams -> 3 distributor formats + injected issues
scripts/etl_pipeline.py              2. extract -> standardize -> 9 validation checks -> load
scripts/evaluate_checks.py           3. score every check against the ground truth + dollar reconciliation
scripts/catalog_valuation.py         4. run-rate, retention curve, concentration, 10-yr DCF
sql/01_schema.sql                    star schema + statement register + exception + quarantine tables
sql/02_analysis_queries.sql          processing status, exception queue, earnings, adjustments
output/etl_run_log.txt               every check with row counts + operational metrics
output/check_evaluation.md           caught vs. missed, and dollar reconciliation
output/valuation_results.md          catalog metrics and valuation
output/statement_register.csv        per-file status (AUTO-PASS / REVIEW / REJECTED)
output/validation_exceptions.csv     the exception queue
```

Run steps 1-4 in order (about 1 minute total).

## Warehouse

- **fact_royalty_line**: one row per statement × track × territory × sale
  month, in local currency and USD, with an `is_adjustment` flag.
- **dim_track** (with `song_id`, see below), **dim_territory**,
  **dim_distributor**, **dim_period** (including `chart_weeks`).
- **statement_register**: one row per file received, with lines in /
  loaded / quarantined and a status.
- **validation_exception**: the review queue, graded HIGH / MEDIUM / LOW.
- **quarantine_line**: lines held back from the fact table until someone
  reviews them. They are never silently dropped.

## Validation checks

| # | Check | What it catches | Action |
|---|---|---|---|
| 1 | Duplicate statement | same content delivered twice under a new file name (content fingerprint, not file bytes) | reject file |
| 2 | Missing statement | a distributor skipped a month | flag HIGH |
| 3 | Duplicate lines | exact re-sent lines inside a statement | remove, log |
| 4 | Footer reconciliation | footer TOTAL ≠ sum of lines | flag HIGH |
| 5 | Missing territory | blank territory code, so the line can't be rated | quarantine |
| 6 | Catalog matching | title+artist lines (no ID) matched after normalizing case/whitespace; multi-ID songs rolled up | match / quarantine |
| 7 | Negative adjustments | reversals & chargebacks, each tied back to the original line it reverses | keep, tag |
| 8 | Rate outliers | effective per-stream rate > 5× or < ⅕ of the peer median (distributor × month × territory) | quarantine |
| 9 | Volume drop | statement streams < 80% of the trailing-3 median | flag MEDIUM |

## Results

### Every injected issue was caught

| Issue | Files injected | Caught | Rows injected | Rows flagged |
|---|---|---|---|---|
| duplicate statement | 1 | 1 | 5,608 | 5,608 |
| missing statement | 1 | 1 | (not delivered) | n/a |
| duplicate lines | 10 | 10 | 237 | 237 |
| footer mismatch (EUR +1,250.00) | 1 | 1 | n/a | n/a |
| missing territory | 9 | 9 | 36 | 36 |
| title format drift | 10 | 10 | 1,007 | 1,073 |
| negative adjustments | 17 | 17 | 67 | 67 (67/67 tied to originals) |
| rate outliers (×100 decimal shift) | 10 | 10 | 30 | 30 |

File-level recall and precision were 1.00 for every issue type. The 66
extra "format drift" rows are not false alarms. They are real casing
variants of titles in the source chart, and they matched correctly after
normalization.

The 30 decimal-shift lines reported **USD 5,158,001.64** where the peer
rate implies **USD 51,580.02**. Quarantining them blocked a **USD 5.1M
overstatement** from reaching the warehouse.

### Issues the checks found in the real data (not injected)

- **One recording, many IDs.** 17,217 Spotify track IDs collapse to
  15,671 songs, and 1,467 songs were released under 2+ IDs (single vs.
  album vs. market-specific releases). Distributor B sends no IDs, so
  20% of its lines (10,024) could not be tied to one ID. A first version
  quarantined them. The final version rolls every line up to a song-level
  `song_id`, which raised B's match rate from **80.05% to 99.998%**
  (50,260 / 50,261). The one line still unmatched has no title or artist
  in the source chart itself.
- **Partial month.** All three October statements came in at 70-73% of
  their trailing median. The cause: the data ends on Oct 18, so October
  has only 3 weekly charts.
- **Uneven months.** Weekly charts start on Fridays, so Mar, May, and Aug
  2019 each hold 5 charts and the other months hold 4. That creates ~25%
  swings that are not real. `dim_period.chart_weeks` stores the count, and
  all trend and valuation work uses earnings per chart week.
- **Coverage gaps in the source.** India is missing 8 of 42 weeks,
  Guatemala and Latvia 1 each, and Cyprus published short charts (184-186
  rows) in two January weeks.

### Dollar reconciliation

Loaded USD was checked against the true earnings implied by the source
streams. **Every dollar of the gap traces to a quarantined line:**

| Distributor | Gap (USD) | Explained by |
|---|---|---|
| A | -51,580.02 | 30 rate-outlier lines at their true value |
| B | -417.38 | 1 unmatched line (EUR 365.47) |
| C | -39,035.86 | 36 missing-territory lines (GBP 30,277.35); June is excluded as not delivered |

### Operational metrics (from `etl_run_log.txt`)

- 30 statement files: **18 AUTO-PASS, 11 REVIEW, 1 REJECTED**
- 165,921 raw lines → **160,009 loaded**, 67 quarantined, and the rest
  were a duplicate file or duplicate lines
- Line-level auto-pass rate: **96.44%**
- Exceptions raised: 73, each with a severity, file, and row count
- Runtime: under 25 seconds end to end on a laptop (varies by run)

### Catalog metrics & valuation (`output/valuation_results.md`)

- **Retention curve.** The share of weekly earnings a song keeps into
  next month was measured for songs whose debut falls inside the data:
  0.96 in the debut month, then 0.71-0.82 in months 1-6. Older catalog
  songs keep 0.81 a month.
- **Concentration.** 3,416 artist catalogs were still earning in Jul-Sep.
  The top 10 hold 23.7% of run-rate and the top 1% hold 40.1%. Each
  catalog also gets top-song and top-territory shares, which measure
  single-hit and single-market risk.
- **Valuation.** A 10-year DCF per catalog projects each song's next 12
  months from its September earnings and its age. After that it applies
  an assumed long-term decline (10% / 20% / 30% sensitivity) and a 10%
  discount rate.
- **Limitation.** Streams are only counted while a song is in a
  country's Top 200, so the measured decline is steeper than real total
  streams. The median value comes out at 0.96× run-rate, which should be
  read as a floor. The ranking and the sensitivity range are the useful
  outputs, not the absolute dollars.

Python (pandas, NumPy, openpyxl), SQL (SQLite star schema, indexes,
