Promotion Impact & Causal Analysis

1,115 stores, 2.5 years of daily sales, one real question: promo days sell more — but how much of that is the promo itself, versus which stores and which seasons happen to run promos more? Hypothesis testing plus a two-way fixed-effects causal design answer it with real confidence intervals, not just a bigger bar in a chart.

00 · Why this project

The one gap a resume audit actually found

Comparing my resume against a Data Scientist posting that explicitly asks for "hypothesis testing, time series analysis, and experimental or causal analysis to identify trends and measure business impact" turned up a real, specific gap. My other projects cover ETL, SQL, dashboarding, and ML modeling, and energy-grid-load-forecasting already covers ML-based time series forecasting — but every comparison across all of them is descriptive ("X is higher than Y"), never a formally designed test of why. This project closes that gap with a real, messy, confounded dataset, not a toy example built to make the causal design look easy.

The core question: Rossmann stores sell noticeably more on days they run a promo. Is that the promo working, or just bigger/busier stores choosing to run promos more often, on particular months and weekdays? Section 03 answers with a real hypothesis test; Section 04 answers with a causal design built specifically to separate the two.

04 · Causal analysis

Two-way fixed effects: the generalized diff-in-diff

Promo isn't randomly assigned: store managers choose which days to run one, and that choice correlates with store size, season, day-of-week, and holidays — all of which independently move sales. A naive promo/non-promo comparison bakes all of that in.

Design

Promo switches on and off for individual stores on individual days throughout the panel — not one simultaneous campaign — so the natural causal design is a two-way fixed-effects regression, the standard generalization of difference-in-differences to panel data with staggered, repeated treatment. Store fixed effects (removed by demeaning — 1,115 levels is too many for dense dummy columns) absorb every time-invariant store trait; year-month fixed effects (31 levels, included directly — valid alongside the demeaned store dimension by the Frisch-Waugh-Lovell theorem) absorb shared seasonal/macro trends; day-of-week and holiday flags are added so the model isn't just comparing more Saturdays in the promo group.

log(1 + Sales) ~ Promo + Store FE + Year-Month FE + Day-of-Week + School Holiday + State Holiday

That's slightly higher than the naive 38.8% pooled gap, not lower — the raw comparison wasn't overstating the promo effect through confounding, it was, if anything, understating it once store-level and seasonal noise are controlled for. Either way, a real, statistically significant promo effect survives the causal design.

Identifying assumption

Conditional parallel trends — absent the promo, a store's sales in a given month would track that month's trend shared across stores, net of its own fixed baseline and calendar pattern. Under that assumption, the store + month fixed effects strip out everything except the promo's own effect.

Threats to that assumption

Strategic timing (reverse causality). If a manager turns on a promo because they privately expect a dip this model can't observe, the estimate would be biased — it would partly capture the manager's private forecast, not the promo's own effect. This dataset can't rule that out directly.

Anticipation / pull-forward effects. Customers may delay or advance purchases around a promo period; this model treats each day independently and doesn't correct for either direction.

Coarse time fixed effects. Year-month (not full daily) fixed effects are used for tractability given 1,115 store dummies already consume the store dimension — a within-month chain-wide event would only be partially absorbed.

Promo2 overlap. A subset of stores also run a separate continuing loyalty program (Promo2) on top of the day-level Promo flag; this model doesn't disentangle the two.

06 · How to run

Reproducing every number on this page

cd scripts
python3 etl_pipeline.py
python3 causal_analysis.py

Requires pandas, numpy, scipy, statsmodels. The ETL script rebuilds output/promotion_dw.db from the raw files; the analysis script re-runs every hypothesis test and refits the causal model, rewriting output/results.md with fresh numbers each time.

sqlite3 output/promotion_dw.db < sql/02_analysis_queries.sql

Tech stack

Python (pandas, numpy, scipy, statsmodels), SQL (SQLite — star schema DDL + analysis queries).
