01 · Why

A risk score alone isn't actionable

Two working systems, built separately, that were never actually talking to each other — until this project connected them.

What the readmission model gives you

A number. "68% risk." Useful for triage, useless for a discharge nurse who needs to know what to actually do differently for this specific patient in the next ten minutes.

What guidelines give you

Hundreds of pages of correct, generic advice — the same page whether the patient is 25 or 85, first admission or fifth. No way to ask "what applies to this patient" without reading it all yourself.

The RAG layer sits between them: retrieve the guideline sections relevant to a question, combine them with this patient's specific risk factors, and let a language model produce one answer that's both evidence-grounded and personalized — instead of picking one property or the other.

02 · Scope

Problem statement

Defined before any code, to keep the build honest about what it is and isn't.

In scopeOut of scope
Diet, exercise, and medication guidance for T2D Diagnosis or treatment decisions
Discharge planning support using guidelines Real-time clinical emergencies
Risk-score-informed, personalized recommendations Prescribing medication directly

Target user

A care team member preparing a discharge plan — not the patient directly, and not a replacement for clinical judgment.

Success criteria

Every answer must be traceable to a specific guideline (no hallucinated advice), must visibly change based on patient context (not a generic template), and must say "not covered" honestly when the guidelines don't address something.

03 · Sources

Building the knowledge base

46 documents across five organizations — chosen for direct relevance to hospital discharge planning, not just topical overlap.

Both peer-reviewed papers use the same UCI Diabetes 130-US Hospitals dataset as the readmission model — chosen deliberately so results could be cross-checked against published benchmarks, not just against themselves.

What each source actually contributes

Not every source plays the same role — clinical protocol, patient-facing explanation, and statistical benchmark each serve a different purpose in the final answer.

ADA — 30 docs

Detailed clinical guidelines — glycemic targets, medication protocols, hospital discharge care

WHO — 7 docs

Global health standards, insulin selection guidelines, essential medicines

CDC — 7 docs

Self-management education (DSMES), prevention programs, clinical guidance

Mayo Clinic — 9 docs

Patient-facing, easy-to-understand explanations — diet, exercise, symptoms

Research Papers — 2 docs

Statistical benchmarks (e.g. "XGBoost AUC 0.667 on a similar dataset") used to cross-check this project's own model results

When a query comes in, the system retrieves the relevant chunks from these 46 documents, combines them with the patient's risk score from the ML model, and the LLM generates a personalized, evidence-based answer — cited back to its source (e.g. "Source: ADA Section 16"). Without these documents, the LLM would answer from its own training data alone — generic and unverifiable. With them, every recommendation is traceable to a trusted medical source.

05 · Building the Dataset

File types & quality checks

Two file types are accepted, three bugs were caught before they reached the vector database — none of it by luck.

What file types this RAG accepts

The pipeline accepts only .pdf and .txt. Anything else is skipped, not errored on.

if file_path.suffix.lower() not in [".pdf", ".txt"]: continue # skip anything that isn't PDF or TXT

Why only these two

Every source guideline was already published in one of these formats — no conversion pipeline needed.

PDF is the native format

ADA, WHO, CDC, and Mayo Clinic all release official documents as PDFs — already the source format, no conversion needed.

TXT was a rare fallback

Used only once — for a paywalled research paper where just the abstract was saved as plain text.

pypdf covers the scope

Reliably extracts text without OCR. Supporting images or slide decks would have meant separate pipelines for unnecessary complexity.

One process, every document

Every file goes through the same extract → chunk process — consistency keeps the pipeline simple and predictable.

This restriction is also what protected the pipeline from one of the bugs below — a file accidentally saved as .jpg instead of .pdf was silently skipped rather than crashing or corrupting the dataset.

Bugs the pipeline caught before they mattered

A naive pipeline run straight from download to embeddings would have silently included bad data. All three were caught by verification steps built into the process.

Exact duplicate file

cdc_ndep.pdf and cdc_national_diabetes_education_program.pdf were the same document under two names. Caught by hashing (MD5) the extracted text of every file — two names, identical hash.

Corrupted file

A research paper saved as .txt actually held raw unreadable PDF binary. Caught by inspecting sample chunk text — the "chunks" were gibberish. Would have produced 245 chunks of pure noise undetected.

Wrong file format

A WHO document was saved as a .jpg screenshot instead of a PDF. Caught by checking file sizes — an 18 KB "document" for a multi-page PDF was an obvious red flag.

Fix applied pipeline-wide: hash-based duplicate detection plus a readability check (printable-character ratio, binary-marker detection) run on every file before the expensive chunking step — constant-time regardless of collection size, so it scales the same at 46 documents or 46,000.

06 · Preprocessing

Recursive chunking

Splitting on paragraph boundaries first, falling back to sentences only when needed — never cutting a clinical value mid-number.

What is chunking, and why does the type matter

A fixed-length split (cut every N words, regardless of what's there) risks separating a threshold from its unit — "180" on one side of a cut, "mg/dL" on the other. Recursive chunking tries the most natural boundary first and only falls back to a smaller one if the piece is still too large:

separators = ["\n\n", "\n", ". ", " ", ""] # tried in this order chunk_size = 350 words overlap = 60 words

Other chunking approaches — and why they weren't the right fit

Four ways to split text into chunks, and the tradeoff each one makes.

TypeWhat it doesWhy it wasn't chosen
Fixed-size Cuts every N words regardless of content Risks splitting medical values (e.g. "140-180 mg/dL") mid-cut — clinically risky
Semantic chunking An embedding model decides topic boundaries Compute-heavy; these documents are already well-structured, making it overkill
Document-structure-based Splits only on headings/sections Some sections (e.g. ADA Section 16) are too long alone — still need further splitting
Recursive chunking Used Tries paragraph → sentence → word, in that order Best of both — respects natural boundaries, with a reliable fallback

Why this matters specifically for retrieval

Retrieval's entire job is finding chunks whose meaning matches a query. That depends on two things:

One complete idea per chunk

Poor chunking splits an idea across two chunks, and retrieval returns incomplete context.

Not too small, not too large

Too small loses context; too large dilutes the similarity score by mixing in unrelated sub-topics — seen earlier when a 350-word chunk scored lower similarity because it covered multiple sub-points.

Why recursive chunking specifically fit this project

Medical accuracy is non-negotiable

Recursive chunking guarantees no clinical value or threshold gets cut mid-number, unlike fixed-size splitting.

Source documents are already well-structured

ADA/WHO/CDC/Mayo guidelines have clear paragraph structure, so the "paragraph-first" approach fits naturally without extra AI processing.

Compatible with the free embedding model's limits

all-MiniLM-L6-v2 has a bounded input size; recursive chunking reliably keeps chunks within it, without the overhead semantic chunking would add.

Predictable and easy to debug

When the data-quality bugs (Section 05) were being tracked down, reading sample chunks was straightforward because the chunking logic was simple and traceable.

Result: 46 documents → 2,456 chunks, each within the 350-word / 60-word-overlap bound.

07 · Embeddings & Retrieval

Meaning as numbers

all-MiniLM-L6-v2 converts each chunk into a 384-number vector, positioned so that semantically similar text ends up numerically close — regardless of exact wording.

The math behind retrieval

cosine_similarity(A, B) = (A · B) / (|A| × |B|)

Worked example — actual numbers

Using 3 numbers per vector to keep the math visible (real embeddings use 384, same formula):

"high blood sugar" → [0.8, 0.6, 0.1] "hyperglycemia" → [0.75, 0.65, 0.05] "chocolate cake" → [-0.3, 0.2, 0.9]
ComparisonSimilarityMeaning
"high blood sugar" ↔ "hyperglycemia" 0.996 Near-identical meaning, zero shared words
"high blood sugar" ↔ "chocolate cake" -0.031 Unrelated

How the model learned this: it was never told which words are related. It trained on masked-word prediction across millions of sentences — words that consistently appear in similar contexts (like "high blood sugar" and "hyperglycemia," both near "insulin," "diabetes," "levels") end up with similar number patterns, discovered from context alone.

What our actual retrieval returned

Query tested: "What should be included in a discharge plan for a high-risk diabetes patient?"

RankSourceSimilarity
1 ADA — Section 16, Diabetes Care in the Hospital 0.468
2 ADA — Diabetes Care in Hospital 0.464
3 ADA — Diabetes Care in Hospital 0.327
4 ADA — Diabetes Care in Hospital 0.318
5 ADA — Diabetes Care in Hospital 0.276

Rank 1 covered hospital-to-outpatient transition guidance; Rank 2 covered medication reconciliation. All 5 results came from ADA specifically — the source most directly focused on hospital discharge protocol.

Why 0.468, not 0.9+ like the worked example above

Two genuine reasons — not a bug:

1. Length and topic dilution

The worked example compared two short, single-topic phrases. A real chunk is a 350-word paragraph covering multiple sub-aspects of discharge planning at once. An embedding averages across every token in the chunk, so when only part of a chunk directly matches the query, the surrounding context spreads the vector rather than keeping it tightly focused. It's topic diversity, not word count, that dilutes the score — a 350-word chunk repeating one single idea would still score high.

2. Query vs. chunk structure mismatch

A question ("What should be included...?") and a paragraph of instructions ("Tailor a structured discharge plan...") have different grammatical shapes. The extra question-words in the query don't have counterparts in the chunk, nudging the vectors slightly apart even when the underlying meaning matches well.

A larger, paid embedding model would normalize this gap better and likely show higher absolute numbers for the same match — but the ranking (which chunk is most relevant) would stay the same.

Similarity rangeWhat it typically means
0.7+ Very strong match — rare, near-identical wording
0.4 – 0.6 Genuinely relevant — normal range for real document retrieval
0.2 – 0.4 Weak or tangential relation
Below 0 Unrelated

0.468 sits squarely in the "genuinely relevant" range — production RAG systems commonly treat 0.3–0.5 as good retrieval when queries are short and source documents are long paragraphs.

Verifying it wasn't a retrieval failure: chunk embeddings were reduced to 2D (PCA) and the actual top-5 retrieved chunks were plotted against the query point. They clustered tightly around it regardless of source — confirming the lower scores were expected model behavior, not a bug.

08 · Personalization Layer

Connecting the two projects

The XGBoost readmission model's own output becomes retrieval context — not a separate, disconnected number sitting next to the chatbot.

The flow

Real patient row → XGBoost predicts risk_score → Rule-based flags → Injected into LLM prompt

What the model actually looks at

The model draws on ~40+ columns from the patient record — prior hospital usage (admissions, emergency visits, outpatient visits), current admission details (time in hospital, discharge disposition), clinical utilization (lab procedures, medication count, diagnoses), diagnosis category, lab results, and the status of 23 individual diabetes medications. Race and gender were deliberately excluded during training to avoid the model learning demographic bias — it decides based on clinical and utilization history alone. The strongest predictors: prior inpatient admissions, discharge disposition, medication count, and length of stay.

Rule-based flags

A small set of rules converts raw model output into explicit priority flags — deliberately rule-based rather than left to the LLM's judgment, since consistency matters more than nuance for safety-relevant triggers.

ConditionFlag raised
risk_score ≥ 0.6 High readmission risk — early follow-up within 7 days
medications > 10 Polypharmacy — medication reconciliation critical
discharged home + prior admissions > 2 Consider home health referral
A1C > 7 Poor glycemic control — reinforce self-management education

Why preprocessing has to happen again for every new patient

A trained model doesn't remember the data it was trained on — a .pkl file stores only learned weights, not a memory of past inputs. The same filtering rule used during training (dropping rows with missing diagnosis codes) has to be reapplied every time a new patient is scored:

# Training (once): raw data → filter/clean → train model → save # Prediction (every time): new patient → SAME filter/clean → trained model → prediction

Why diagnosis codes specifically, and not other missing fields

# Filled with a placeholder category df['payer_code'] = df['payer_code'].fillna('Unknown') # Rows dropped entirely if missing df = df.dropna(subset=['diag_1', 'diag_2', 'diag_3'])

For fields like payer_code, "Unknown" is a genuinely valid category. A missing diagnosis code can't be meaningfully filled — it's the core clinical signal driving readmission risk, and training followed the same drop-if-missing rule.

One extra step needed here that training didn't require

df_encoded = df_encoded.reindex(columns=model_columns, fill_value=0)

Training one-hot encoded all 101,766 rows together, so every possible category naturally became a column. Encoding a single patient row at a time means a rare category the patient doesn't have simply won't get created — even though the trained model still expects that column to exist. reindex() fills in any missing expected columns with 0, keeping the input format identical to what the model was trained on.

A bug that caught itself

Filtering out rows with missing diagnosis codes broke the alignment between a row's label (its original ID) and its position (1st, 2nd, 3rd... remaining row after filtering). The first version of the test function used .iloc, which selects by position:

sample_patient_raw = valid_rows.iloc[[38790]] # BUG: treats 38790 as a position, not a label

This silently returned a different patient. No error, no crash — the code ran fine.

How it was caught: the same patient's risk score, computed two different ways, didn't match.

MethodRisk score
Batch scoring (correct patient) 70.7%
Individual test with .iloc (wrong patient) 16.8%

The fix

sample_patient_raw = valid_rows.loc[[38790]] # FIX: selects by actual row label

After the fix, patient 38790's risk score came out consistently at 55.4%.

Validation — real patients, real difference

The low-risk patient triggered minimal flags; the high-risk patient triggered both polypharmacy and home-health flags — confirming the personalization layer responds to actual patient data, not a fixed template.

PatientRisk scorePrior admissionsMedicationsFlags triggered
A 12.6% 0 11 Polypharmacy only
B 55.4% 4 13 Polypharmacy + Home health referral

10 · Shipping It

From notebook to live app

Streamlit Community Cloud, with the entire pipeline — retrieval, personalization, generation — running behind one page.

Architecture

Deployment issues, in order

1. Missing dependencies

First deploy crashed with ModuleNotFoundError for xgboost, since the pickled model needs the library installed to unpickle, not just to train. Fix: added xgboost and scikit-learn to requirements.txt.

2. Hidden dependency

A second crash surfaced No module named 'torchvision', pulled in internally by sentence-transformers even though the app never touches images. Fix: added torchvision to requirements.txt.

3. Public repo, private token

The Hugging Face token couldn't be hardcoded (repo is public on GitHub) or asked from every visitor (adds friction). Fix: moved to Streamlit Cloud's encrypted Secrets store (st.secrets["HF_TOKEN"]) — never exposed in the repo or shown in the UI.

A CSS lesson worth keeping

Several rounds of styling the send button used the modern :has() CSS selector. It looked correct and produced no errors — it just silently did nothing, because :has() isn't universally supported across browser versions, and an unsupported selector doesn't fail loudly, it's just ignored. Switching to :focus-within and :last-child (both universally supported) fixed what multiple rounds of pixel-tweaking couldn't.

Separately, Streamlit's official key= parameter (which generates a stable .st-key-<name> CSS class) turned out to be far more reliable for custom styling than guessing at Streamlit's internal DOM structure.

Why an iframe embed, not a rebuild

The live app is embedded on this page via <iframe src="...?embed=true"> — Streamlit's officially supported embed method — rather than rebuilding the UI in plain HTML. True auto-resizing isn't possible across origins without the embedded site sending a resize signal, which Community Cloud embeds don't do — so the box is manually resizable instead (drag the corner) as a practical compromise.

11 · Honesty Check

Limitations

Same standard applied here as in the readmission model — state the gaps rather than gloss over them.

LimitationWhat it meansSeverity
Free embedding model Smaller, less precise than paid alternatives — retrieval ranking stays correct, but similarity scores read lower (~0.4–0.6, not 0.9+) than a larger model would produce for the same match Medium
Free-tier LLM Runs on Hugging Face's free inference (Llama-3.1-8B-Instruct); a paid frontier model would likely improve reasoning quality and reduce occasional wording ambiguity Medium
Guidelines are ADA/WHO/CDC/Mayo only No hospital-specific protocols or medication formularies — general guidance, not a substitute for local clinical policy By design
Inherits the base model's caveats Patient-level leakage and dataset age (see the original readmission project) apply here too, since risk scores feed directly into this system High
No auto-resizing embed The embedded app box on this page can't automatically grow when the patient form expands — a cross-origin browser restriction, not a bug — visitors can drag-resize it manually By design

Bottom line: this is a working proof-of-concept that demonstrates the architecture end-to-end — a real predictive model, real retrieval over real guidelines, and a real personalization layer connecting them. It is not clinically validated, and the same "screening aid, not diagnostic tool" framing from the base model applies here with equal force.
