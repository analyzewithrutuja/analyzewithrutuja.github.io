# Promotion Impact & Causal Analysis

An end-to-end data engineering + statistics project that turns 2.5 years of
raw daily retail sales into a small SQL data warehouse and a rigorous answer
to a question every retail/marketing analytics team asks: *"does running a
promo actually cause higher sales, or are we just watching sales that were
already going to be higher?"* — built to practice the exact statistical
workflow (hypothesis testing + causal/experimental design) a Data Scientist
role expects, not just descriptive charts.

## Why this project

I built this after comparing my resume against a Data Scientist posting that
explicitly asks for "hypothesis testing, time series analysis, and
experimental or causal analysis to identify trends and measure business
impact." My background covers ETL, SQL, dashboarding, and ML modeling, and
`energy-grid-load-forecasting/` already covers ML-based time series
forecasting, but I had **nothing that demonstrated formal hypothesis testing
or causal inference** — every comparison in my other projects is descriptive
("X is higher than Y"), not a designed test of *why*. This project is that
gap, closed with a real, messy, confounded dataset rather than a clean toy
example built to make the causal design look easy.

## Data source

**Rossmann Store Sales** — daily sales for 1,115 Rossmann drug stores across
Germany, January 2013 – July 2015 (1,017,209 raw rows), including a daily
`Promo` flag, state/school holiday indicators, store type, assortment level,
and distance to the nearest competitor. Originally published as a Kaggle
competition
([kaggle.com/c/rossmann-store-sales](https://www.kaggle.com/c/rossmann-store-sales)),
sourced here via a public GitHub mirror
([dmi3kno/Kaggle-Rossmann](https://github.com/dmi3kno/Kaggle-Rossmann)) so no
Kaggle account/API key is required — the same approach
`energy-grid-load-forecasting/` used for its PJM data. Both mirrored files
(`train.csv`, `store.csv`) were verified against the known, published shape
of this dataset (1,017,209 sales rows, 1,115 stores) before use. Raw files
are kept at `data/raw/train.csv` and `data/raw/store.csv`.

This dataset is a better fit for a causal-impact project than it might first
look: `Promo` is a day-level decision made independently by each store, not
a single simultaneous campaign, which is exactly the "staggered treatment"
shape that a fixed-effects causal design is built for — and unlike a
purpose-built A/B test dataset, nothing here was randomized, so the
confounding is real and has to be actually dealt with, not just described.

## Architecture

```
data/raw/                       train.csv (1.02M rows) + store.csv (1,115 stores)
scripts/etl_pipeline.py         Extract -> clean/standardize -> load
scripts/causal_analysis.py      hypothesis tests + two-way FE causal model + light seasonality view
sql/01_schema.sql                star-schema DDL
sql/02_analysis_queries.sql      BI queries (incl. the confounds the causal model controls for)
output/promotion_dw.db           finished SQLite data warehouse
output/results.md                every statistic below, generated by causal_analysis.py
output/etl_run_log.txt           data-quality log from the last ETL run
```

Same hybrid ETL/ELT shape as the other two SQL-based projects in this
portfolio: cleaning and dimension-building happen in pandas, the result is
loaded into a SQL star schema, and the statistical/causal analysis reads
back out of that warehouse via SQL — not straight from the raw CSVs — so the
numbers below are reproducible from the warehouse alone.

## Star schema

```
                Dim_Date
                    |
                    |
Dim_Store -----  Fact_Daily_Sales
 (type,            |
  assortment,  Sales, Customers,
  competition) Promo, Is_Sales_Anomaly
```

- **Fact_Daily_Sales** — one row per (store, day) the store was open.
  Measures: sales, customers, the `Promo` treatment flag, plus a
  data-quality flag carried through rather than silently dropped.
- **Dim_Date** — calendar dimension (year, month, `Year_Month` used as the
  time fixed-effect key, day-of-week, weekend flag, state/school holiday
  type).
- **Dim_Store** — the 1,115 stores, with store type, assortment level,
  competition distance, and the separate continuing `Promo2` loyalty-program
  flag.

## ETL / data-quality decisions worth calling out

- **Closed-store non-days excluded.** `Open=0` rows (172,817 of 1,017,209 —
  about 17%) are days the store didn't trade at all; sales is 0 by
  definition on every one of them and they carry no information about a
  promo's effect on sales. Excluding them matches how the original
  competition itself scored results.
- **Open-but-zero-sales anomaly, flagged not dropped.** 54 rows report
  `Open=1` with `Sales=0` — almost certainly a register/reporting glitch
  rather than a real zero-revenue trading day. These are kept in the
  warehouse (`Is_Sales_Anomaly=1`) for auditability but excluded from the
  statistical/causal scripts, the same "flag, don't silently drop" pattern
  used for DST artifacts in `energy-grid-load-forecasting/`.
- **CompetitionDistance imputed for 3 stores, flagged.** Missing distance
  was filled with the max observed distance (75,860m) as a "no known nearby
  competitor" proxy rather than the mean, which would understate how
  isolated those stores actually are — and flagged
  (`Is_Competition_Distance_Imputed`) so the imputation is traceable.
  `CompetitionOpenSinceMonth/Year` (missing for 354 stores) is left null
  rather than imputed — this project's causal model doesn't use it, and
  inventing a date would add fake precision for no benefit.
  `Promo2SinceWeek/Year/Interval` (missing for 544 stores) isn't actually
  missing data at all — it's null by construction wherever `Promo2=0`.
- **StateHoliday re-encoded.** The raw field mixes a string `'0'` (meaning
  *not* a holiday) with `'a'/'b'/'c'` holiday-type codes — an easy field to
  misread as falsy-but-present. Standardized into a readable category
  (`None`/`Public`/`Easter`/`Christmas`) plus an explicit boolean flag.

Every decision above is logged with a row count in `output/etl_run_log.txt`
on each run.

## Statistical analysis

Full numbers (test statistics, p-values, confidence intervals) are in
`output/results.md`, generated fresh by `causal_analysis.py` on every run —
not retyped by hand. Summary below; sample is 844,338 store-days (open-store
days, anomaly rows excluded) across 1,115 stores, Jan 2013 – Jul 2015.

### 1. Hypothesis testing — is the promo/sales gap real?

Promo days average **8,229** in sales vs. **5,930** on non-promo days — a
raw **38.8%** gap. Tested four ways:

| Test | Statistic | p-value | Effect size |
|---|---|---|---|
| Welch's t-test (pooled daily obs.) | t = 356.69 | < 1e-300 | Cohen's d = 0.797 |
| Mann-Whitney U (pooled, nonparametric) | U = 1.31×10¹¹ | < 1e-300 | — |
| Paired t-test (one pair per store — clustering-safe) | t = 74.98 | < 1e-300 | Cohen's d = 2.245 |
| Wilcoxon signed-rank (store-level pairs) | W = 6 | 5.98e-184 | — |

The pooled tests treat 844K daily rows as independent, which overstates
significance since the same store's promo days are correlated with each
other (pseudo-replication). The paired tests collapse each store to one
promo-mean-vs-non-promo-mean pair first — **1,114 of 1,115 stores (99.9%)**
sell more on their own promo days than their own non-promo days. All four
agree the gap is statistically significant well beyond any conventional
threshold. That's association, not yet causation — which is exactly what
Section 2 addresses.

### 2. Causal analysis — how much of that gap is actually caused by the promo?

`Promo` isn't randomly assigned: store managers choose which days to run
one, and that choice correlates with store size, season, day-of-week, and
holidays — all of which independently move sales. A naive promo/non-promo
comparison bakes all of that in.

**Design: two-way fixed-effects regression** (the standard generalization of
difference-in-differences to panel data with staggered, repeated
treatment — `Promo` switches on/off per store per day throughout the panel,
not as one simultaneous campaign). Store fixed effects (removed by
demeaning — 1,115 levels is too many for dense dummy columns) absorb every
time-invariant store trait; year-month fixed effects (31 levels, included
directly — valid by the Frisch-Waugh-Lovell theorem alongside the demeaned
store dimension) absorb shared seasonal/macro trends; day-of-week and
state/school holiday flags are added so the model isn't just comparing more
Saturdays in the promo group.

```
log(1 + Sales) ~ Promo + Store FE + Year-Month FE + Day-of-Week + School Holiday + State Holiday
standard errors clustered by store (1,115 clusters)
```

**Result: Promo coefficient = 0.3312 log points (cluster-robust SE 0.0026,
p < 1e-300) → an estimated 39.3% causal lift in sales (95% CI: 38.5% to
40.0%).**

That's slightly *higher* than the naive 38.8% pooled gap, not lower — the
raw comparison wasn't overstating the promo effect through confounding, it
was, if anything, understating it once store-level and seasonal noise are
controlled for. Either way, a real, statistically significant promo effect
survives the causal design.

**Identifying assumption: conditional parallel trends** — absent the promo,
a store's sales in a given month would track that month's trend shared
across stores, net of its own fixed baseline and calendar pattern. Real
threats this dataset can't rule out: **strategic timing** (a manager turning
on a promo *because* they privately expect a dip would bias the estimate),
**anticipation/pull-forward effects** (customers delaying or advancing
purchases around a promo, untested here), **coarse year-month time fixed
effects** (a within-month chain-wide event would only be partially
absorbed), and **`Promo2` overlap** (a separate continuing loyalty program
this model doesn't disentangle from the day-level `Promo` flag). These are
stated explicitly rather than glossed over — full discussion in
`output/results.md`.

### 3. Supporting view — weekly seasonality (brief, not the headline)

A short classical decomposition for two representative stores, included
only as a sanity check that the day-of-week control above is doing real
work — ML-based time series forecasting is the headline technique in
`energy-grid-load-forecasting/`, not repeated here. Store 817 (highest
average sales, 21,464/day) shows a 10,296 weekly seasonal swing (48% of its
average); Store 1 (4,816/day) shows a much smaller 645 swing (13%) —
confirming day-of-week effects vary meaningfully by store and are worth
controlling for, not just assuming away.

## How to run

```bash
cd scripts
python3 etl_pipeline.py
python3 causal_analysis.py
```

Requires `pandas`, `numpy`, `scipy`, `statsmodels` (`pip install pandas
numpy scipy statsmodels`). Running the ETL script rebuilds
`output/promotion_dw.db` from the raw files and reprints the data-quality
log; the analysis script re-runs every hypothesis test and refits the
causal model, rewriting `output/results.md` with fresh numbers each time.

To explore the warehouse directly:

```bash
sqlite3 output/promotion_dw.db < sql/02_analysis_queries.sql
```

## Tech stack

Python (pandas, numpy, scipy, statsmodels), SQL (SQLite — star schema DDL +
analysis queries).
